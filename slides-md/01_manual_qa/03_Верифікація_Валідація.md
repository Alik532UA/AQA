# Верифікація / Валідація

> **Підтеми:** Техніки тест-дизайну, Severity vs Priority

**Категорія:** Manual QA

---

## Verification | Верифікація

Verification — 'is the system correct to specification?'

Верифікація — чи відповідає система специфікаціям?

це процес оцінки системи або її компонентів з метою визначення, чи задовольняють результати поточного етапу умовам, сформованим на початку цього етапу [IEEE]. Тобто чи виконуються цілі, терміни та завдання поточної фази.

---

## Validation | Валідація

Validation — 'Are we building the right product?'

Валідація — «Чи правильний продукт ми розробляємо?»

це оцінка відповідності розроблюваного ПЗ очікуванням, потребам користувача та бізнес-вимогам [BS7925-1 / ISTQB].

Верифікація — «Чи правильно ми створюємо продукт?» (відповідність ТЗ/специфікаціям). Валідація — «Чи правильний продукт ми створили?» (відповідність потребам користувачів).

---

## Техніки тест-дизайну | Design test techniques

**Еквівалентний поділ (Equivalence Partitioning — EP):**
розподіл вхідних даних на класи: валідні (всередині діапазону) та невалідні (поза діапазоном). Наприклад, для 1..10: обрати 5 (валідний), 0 та 11 (невалідні).

**Аналіз граничних значень (Boundary Value Analysis — BVA):**
перевірка меж та значень біля них (для 1..10: граничні точки 0, 1, 10, 11).

**Таблиці рішень (Decision Table Testing):**
структурування складних бізнес-правил та комбінацій вхідних умов для вибору дій системи.

**Діаграма переходів станів (State Transition Testing):**
перевірка переходів між різними життєвими циклами об'єкта (наприклад: New → In Progress → Closed).

**Попарне тестування (Pairwise Testing):**
оптимальний набір комбінацій, де кожна пара значень параметрів тестується щонайменше один раз.

**Передбачення помилки (Error Guessing — EG):**
досвід та інтуїція тестувальника: «Що буде при некоректному форматі даних чи порожніх полях?»

**Вичерпне тестування (Exhaustive Testing — ET):**
перевірка всіх можливих комбінацій. Практично неможливе (принцип ISTQB №2).

## Severity vs Priority

**Серйозність (Severity)** — атрибут, що характеризує технічний вплив дефекту на працездатність програми (виставляється тестувальником).

**Пріоритет (Priority)** — атрибут, що вказує на черговість виконання завдання або усунення дефекту для бізнесу (виставляється менеджером, Product Owner, лідом або замовником).

### Градація Серйозності дефекту (Severity):

- **S1 Блокуюча (Blocker):** повна зупинка системи або критичної функції, робота з програмою неможлива, тестування заблоковано.

- **S2 Критична (Critical):** не працює ключова бізнес-логіка, діра в безпеці, падіння сервера без можливості обходу (no workaround).

- **S3 Значна (Major):** частина логіки працює некоректно, але є обхідний шлях (workaround).

- **S4 Незначна (Minor):** не порушує бізнес-логіку, очевидна невідповідність інтерфейсу (UI).

- **S5 Тривіальна (Trivial):** малопомітна проблема UI, одруківка в тексті, не впливає на загальну якість.

### Градація Пріоритету дефекту (Priority):

- **P1 Високий (High):** виправити якнайшвидше, критично для релізу/проекту.

- **P2 Середній (Medium):** не блокує реліз, але обов'язкове до виправлення.

- **P3 Низький (Low):** не вимагає термінового виправлення, за наявності часу.
